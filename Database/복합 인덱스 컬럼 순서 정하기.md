# 복합 인덱스 컬럼 순서 정하기

> 한 줄 요약: **순서 규칙은 "카디널리티 높은 것 먼저"가 아니라 `= 조건 먼저 → 정렬 컬럼 → 범위 조건 마지막`이다.** 카디널리티는 그 다음에 보는 보조 기준.

[[클러스터 인덱스 vs 비클러스터 인덱스]] / [[인덱스가 많으면 쓰기가 느려지는 이유]] 의 후속 노트.

---

# 1. 복합 인덱스 = 정렬된 전화번호부

```sql
CREATE INDEX idx_abc ON users(city, name, age);
```

이건 인덱스 3개가 아니라, **`city`로 먼저 정렬하고 → 같으면 `name`으로 → 그래도 같으면 `age`로 정렬한 목록 1개**다.

```
idx_abc (city, name, age)
─────────────────────────
부산, 김철수, 28
부산, 이순신, 52
서울, 강감찬, 30
서울, 김철수, 25
서울, 김철수, 41     ← city·name 이 같으니 age 로 정렬
서울, 박영희, 33
```

전화번호부가 **"지역 → 이름" 순으로 정렬**돼 있는 것과 같다. 모든 규칙이 여기서 따라 나온다.

---

# 2. 왼쪽 접두사 규칙 (가장 중요)

전화번호부에서 **"지역은 모르고 이름만 아는 사람"은 못 찾는다.** 앞에서부터 순서대로 알아야 한다.

`idx_abc (city, name, age)` 기준:

| 쿼리 조건 | 인덱스 사용 | 이유 |
| --- | --- | --- |
| `WHERE city='서울'` | ✅ | 맨 앞부터 시작 |
| `WHERE city='서울' AND name='김철수'` | ✅ | 앞에서 2개 연속 |
| `WHERE city='서울' AND name='김철수' AND age=25` | ✅ 전부 | 3개 다 |
| `WHERE name='김철수'` | ❌ | `city`를 건너뜀 → 풀스캔 |
| `WHERE age=25` | ❌ | 마찬가지 |
| `WHERE city='서울' AND age=25` | 🔸 `city`까지만 | 중간의 `name`이 비어서 `age`는 탐색에 못 씀. 좁힌 뒤 필터링만 |

> **핵심**: 인덱스는 **왼쪽부터 끊기지 않고 연속으로** 조건이 주어질 때만 탄다.
> 그래서 `(a, b)` 인덱스가 있으면 `(a)` 단독 인덱스는 불필요하고, `(b)` 단독은 따로 필요할 수 있다.

## `AND` 를 쓴 순서는 상관없다

```sql
WHERE name='김철수' AND city='서울'   -- 이것도 인덱스 잘 탄다
```

**쿼리에 적은 순서**가 아니라 **인덱스에 정의된 순서**가 기준이다. 옵티마이저가 알아서 맞춰준다.

---

# 3. 순서 정하는 3단계 규칙

## 1순위 — 등치(`=`) 조건 컬럼을 앞에, 범위 조건을 뒤에

가장 중요한 규칙. **범위 조건(`>`, `<`, `BETWEEN`, `LIKE 'abc%'`)을 만나는 순간 그 뒤 컬럼은 인덱스 탐색에 못 쓰인다.**

```sql
SELECT * FROM orders
WHERE user_id = 100 AND created_at >= '2026-09-01';
```

```sql
-- ❌ 나쁨: 범위가 앞
CREATE INDEX idx_bad ON orders(created_at, user_id);
```

```
created_at >= '2026-09-01' 구간 = 9월 주문 전체 10만 건
→ 그 10만 건을 훑으며 user_id=100 인지 하나씩 확인
```

```sql
-- ✅ 좋음: 등치가 앞
CREATE INDEX idx_good ON orders(user_id, created_at);
```

```
user_id=100 구간(50건)으로 먼저 좁힘
→ 그 구간 안은 created_at 순 정렬이므로 9월 부분만 범위 스캔
→ 실제로 읽는 행 = 딱 필요한 만큼
```

> 왜? 2단계 정렬이라 **`user_id`가 같은 구간 안에서만** `created_at`이 정렬돼 있다. `user_id`가 고정돼야 `created_at`이 쓸모 있어진다.

## 2순위 — `ORDER BY` / `GROUP BY` 컬럼을 그 다음에

등치 조건 뒤에 정렬 컬럼을 두면 **정렬 작업 자체가 사라진다** (인덱스가 이미 정렬돼 있으므로).

```sql
SELECT * FROM posts
WHERE board_id = 5
ORDER BY created_at DESC
LIMIT 20;

CREATE INDEX idx_board_created ON posts(board_id, created_at);
-- EXPLAIN 에서 Using filesort 가 사라짐 → 앞 20건만 읽고 즉시 종료
```

## 3순위 — 남는 자리에선 카디널리티 높은 컬럼을 앞으로

**1·2순위로 순서가 안 정해질 때만** 쓰는 보조 기준이다. 등치 조건 컬럼이 여러 개라면 더 잘게 쪼개는(= 중복이 적은) 컬럼을 앞에 둔다.

| 컬럼 | 고유값 수 (100만 행 기준) | 카디널리티 |
| --- | --- | --- |
| `email` | 1,000,000 | 매우 높음 |
| `user_id` | 50,000 | 높음 |
| `city` | 250 | 중간 |
| `status` | 4 | 낮음 |
| `is_deleted` | 2 | 매우 낮음 |

```sql
WHERE status = 'paid' AND user_id = 100   -- 둘 다 등치

-- ✅ user_id(5만 종)가 앞
CREATE INDEX idx ON orders(user_id, status);
-- user_id=100 으로 20건까지 좁힌 뒤 status 확인

-- 🔸 반대 순서면 status='paid' 로 30만 건까지밖에 못 좁힘
```

## 카디널리티 확인하는 법

```sql
-- MySQL: 인덱스별 추정 카디널리티
SHOW INDEX FROM orders;   -- Cardinality 컬럼 (통계 기반 추정치)

-- 직접 세보기 (정확)
SELECT COUNT(DISTINCT user_id), COUNT(DISTINCT status), COUNT(*) FROM orders;
```

```sql
-- PostgreSQL (n_distinct 가 음수면 전체 행 대비 비율)
SELECT attname, n_distinct FROM pg_stats WHERE tablename = 'orders';
```

# 4. "카디널리티 높은 걸 앞에"가 틀리는 경우

흔히 1순위처럼 알려져 있지만 3순위인 이유가 있다.

## 사례 A — 카디널리티가 낮아도 항상 `=` 조건이면 앞에 와도 된다

```sql
-- 이 쿼리만 계속 돈다
SELECT * FROM posts
WHERE status = 'published'        -- 고유값 3개뿐 (카디널리티 낮음)
ORDER BY created_at DESC LIMIT 20;

CREATE INDEX idx ON posts(status, created_at);  -- ✅ 맞는 설계
```

`status`는 카디널리티가 낮지만 **항상 등치 조건**이다. 앞에 두면 뒤의 `created_at`이 정렬 상태로 이어져 `ORDER BY` + `LIMIT 20`이 사실상 공짜가 된다. 반대로 `(created_at, status)`면 전체를 훑어야 한다.

> 낮은 카디널리티 컬럼이 나쁜 건 **단독 인덱스**일 때다 (`INDEX(status)` 하나만 있으면 옵티마이저가 안 쓴다).
> 복합 인덱스의 **선두**로는, 항상 `=` 로 들어오고 뒤에 범위·정렬 컬럼이 따라붙는다면 훌륭한 선택이다.

## 사례 B — 여러 쿼리가 나눠 쓸 접두사

```sql
-- 쿼리1: WHERE user_id = ?
-- 쿼리2: WHERE user_id = ? AND status = ?
-- 쿼리3: WHERE user_id = ? AND status = ? AND created_at >= ?

CREATE INDEX idx ON orders(user_id, status, created_at);  -- 이거 하나로 3개 다 처리
```

카디널리티만 따지지 말고 **왼쪽 접두사를 여러 쿼리가 공유하도록** 설계하면 인덱스 개수를 줄일 수 있다. 인덱스 1개 줄이는 건 그대로 쓰기 성능 이득이다 ([[인덱스가 많으면 쓰기가 느려지는 이유]]).

# 5. 실전 예제 3개

## 예제 1 — 게시판 목록

```sql
SELECT id, title, created_at FROM posts
WHERE board_id = 5 AND status = 'published'
ORDER BY created_at DESC
LIMIT 20;
```

| 단계 | 판단 |
| --- | --- |
| 등치 조건 | `board_id`, `status` → 앞쪽 |
| 둘 중 순서 | `board_id`(수백 종) > `status`(3종) → `board_id` 먼저 |
| 정렬 | `created_at` → 등치 뒤 |
| 커버링 | `id`는 PK라 자동 포함, `title`까지 넣으면 룩업도 제거 |

```sql
CREATE INDEX idx_posts_list ON posts(board_id, status, created_at);
-- 더 욕심내면 (board_id, status, created_at, title) → Extra: Using index
```

## 예제 2 — 기간별 주문 조회

```sql
SELECT * FROM orders
WHERE user_id = 100
  AND status IN ('paid', 'shipped')
  AND created_at BETWEEN '2026-09-01' AND '2026-09-30'
ORDER BY created_at DESC;
```

```sql
CREATE INDEX idx_orders_user ON orders(user_id, status, created_at);
```

- `user_id` — 등치 + 카디널리티 최고 → 1번
- `status` — `IN`은 등치 여러 개로 취급되어 인덱스를 탄다 → 2번
- `created_at` — 범위 → **반드시 마지막**

## 예제 3 — 로그인

```sql
SELECT id, password_hash FROM users
WHERE email = 'a@x.com' AND is_active = 1;
```

```sql
CREATE UNIQUE INDEX uq_users_email ON users(email);   -- ✅ 이걸로 충분
```

`email`이 유니크라 이미 1건으로 확정된다. `is_active`를 뒤에 붙여도 얻는 게 없고 인덱스만 커진다. **카디널리티 최고인 컬럼으로 1건이 확정되면 거기서 끝낸다.**

# 6. `EXPLAIN` 으로 순서가 맞는지 검증

```sql
EXPLAIN SELECT * FROM orders WHERE user_id=100 AND created_at >= '2026-09-01';
```

| 볼 것 | 좋은 신호 | 나쁜 신호 |
| --- | --- | --- |
| `key` | 의도한 인덱스 이름 | `NULL` (인덱스 미사용) |
| `key_len` | 클수록 앞쪽 컬럼을 많이 활용 | 예상보다 작으면 **뒤쪽 컬럼이 안 쓰이는 중** |
| `rows` | 실제 결과 건수에 근접 | 수십 배 크면 순서가 잘못됨 |
| `Extra` | `Using index` (커버링) | `Using filesort` → 정렬 컬럼 위치가 틀림 |

## `key_len` 읽는 법

```
-- INDEX(user_id BIGINT NOT NULL, status TINYINT NOT NULL, created_at DATETIME NOT NULL)
-- 각각 8 + 1 + 5 바이트

key_len = 8   → user_id 까지만 사용
key_len = 9   → user_id + status
key_len = 14  → 3개 전부
```

의도한 것보다 작으면 컬럼 순서나 조건 형태를 다시 본다. (NULL 허용 컬럼은 +1바이트, 가변길이 문자열은 +2바이트가 붙는다)

# 7. 순서를 잘 잡아도 인덱스가 끊기는 경우

```sql
-- ❌ 컬럼에 함수·연산을 씌우면 그 컬럼부터 끊긴다
WHERE DATE(created_at) = '2026-09-21'
-- ✅
WHERE created_at >= '2026-09-21' AND created_at < '2026-09-22'

-- ❌ 앞에 와일드카드가 있는 LIKE
WHERE name LIKE '%철수'
-- ✅ 접두사 검색만 인덱스를 탄다
WHERE name LIKE '김%'

-- ❌ 타입 불일치 (문자 컬럼에 숫자 비교 → 암묵 형변환)
WHERE phone = 01012345678
-- ✅
WHERE phone = '01012345678'

-- ❌ OR 는 인덱스를 끊기 쉽다
WHERE user_id = 1 OR email = 'a@x.com'
-- ✅ UNION 으로 각각 인덱스를 태운다
SELECT ... WHERE user_id = 1
UNION
SELECT ... WHERE email = 'a@x.com'
```

# 8. SQLAlchemy 정의

```python
from datetime import datetime
from sqlalchemy import BigInteger, String, DateTime, Index
from sqlalchemy.orm import Mapped, mapped_column

class Order(Base):
    __tablename__ = "orders"

    id: Mapped[int] = mapped_column(BigInteger, primary_key=True)
    user_id: Mapped[int] = mapped_column(BigInteger)
    status: Mapped[str] = mapped_column(String(20))
    created_at: Mapped[datetime] = mapped_column(DateTime)

    __table_args__ = (
        # 등치(user_id, status) → 범위·정렬(created_at) 순서
        Index("idx_orders_user", "user_id", "status", "created_at"),
    )
```

> `Index(...)` 의 인자 순서가 그대로 DDL 컬럼 순서다. 모델의 컬럼 선언 순서와는 무관하다.
