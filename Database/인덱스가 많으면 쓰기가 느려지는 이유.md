# 인덱스가 많으면 쓰기가 느려지는 이유

> 한 줄 요약: **인덱스 N개 = INSERT 1건에 B-Tree N+1개를 고쳐 쓰는 일.** 읽기를 위해 쓰기를 파는 거래다.

[[클러스터 인덱스 vs 비클러스터 인덱스]] 의 후속 노트.

---

# 1. 결론부터

모든 컬럼에 인덱스를 걸면 **쓰기는 확실히 느려진다.** 그리고 느려지는 이유가 하나가 아니라 5가지가 겹친다.

| # | 비용 | INSERT | UPDATE | DELETE |
| --- | --- | --- | --- | --- |
| 1 | B-Tree 갱신 × 인덱스 수 | ✅ 전부 | 바뀐 컬럼의 인덱스만 | ✅ 전부 |
| 2 | 페이지 분할 / 재균형 | ✅ | ✅ | (병합) |
| 3 | 랜덤 I/O (인덱스마다 다른 페이지) | ✅ | ✅ | ✅ |
| 4 | redo/undo·WAL 기록량 증가 | ✅ | ✅ | ✅ |
| 5 | 버퍼풀·캐시 오염 | ✅ | ✅ | ✅ |

---

# 2. 왜 느려지나 — 5가지 비용

## 2-1. 인덱스 개수만큼 트리를 고친다

`users` 에 인덱스가 5개(PK + 세컨더리 4개) 있다고 하면, `INSERT` 1건은:

```
INSERT INTO users (email, name, phone, status, created_at) VALUES (...);

1. 클러스터 인덱스에 행 삽입            ← 데이터 본체
2. idx_email   트리에 (email → PK) 삽입
3. idx_name    트리에 (name → PK) 삽입
4. idx_phone   트리에 (phone → PK) 삽입
5. idx_status  트리에 (status → PK) 삽입
```

**쓰기 증폭(write amplification)**. 행 하나 넣는데 5곳이 갱신된다. 인덱스 10개면 10곳.

## 2-2. 페이지 분할 (page split)

B-Tree 리프 페이지가 꽉 찬 상태에서 중간에 값이 들어오면, 페이지를 둘로 쪼개고 부모 노드도 갱신한다.

- `created_at`, `AUTO_INCREMENT` 처럼 **증가하는 값** → 항상 오른쪽 끝에 append, 분할 거의 없음
- `email`, `uuid`, `name` 처럼 **무작위 값** → 삽입 위치가 트리 전체에 흩어짐 → 분할 빈번 → 단편화

즉 **인덱스 컬럼의 성격**에 따라 비용이 몇 배 차이 난다. 무작위 문자열 컬럼 인덱스가 가장 비싸다.

## 2-3. 랜덤 I/O

인덱스 5개는 디스크상 서로 다른 5개 영역이다. 순차 쓰기 1번이 랜덤 쓰기 5번이 된다. SSD라 체감이 덜할 뿐 사라지지 않는다.

> InnoDB의 **Change Buffer**가 이걸 완화한다 — 비유니크 세컨더리 인덱스 갱신은 일단 메모리에 모아뒀다가 나중에 병합한다.
> **단, UNIQUE 인덱스는 중복 검사를 해야 해서 Change Buffer를 못 쓴다.** 해당 페이지를 즉시 디스크에서 읽어와야 한다.
> → **불필요한 UNIQUE는 쓰기에 특히 비싸다.**

## 2-4. 로그 기록량 증가

갱신된 페이지는 전부 redo log(InnoDB) / WAL(PostgreSQL)에 기록된다. 인덱스가 많으면 트랜잭션당 로그량이 늘고, 복제 지연·체크포인트 부하·백업 크기까지 같이 커진다.

## 2-5. 버퍼풀 오염

인덱스도 메모리(버퍼풀)를 먹는다. 안 쓰는 인덱스가 메모리를 차지하면 정작 필요한 데이터 페이지가 밀려나고, 그만큼 디스크 접근이 늘어 **읽기까지 같이 느려진다.**

# 3. UPDATE는 조금 다르다

MySQL/InnoDB는 **바뀐 컬럼을 포함한 인덱스만** 갱신한다.

```sql
-- idx_email, idx_name, idx_phone 이 있을 때
UPDATE users SET last_login_at = NOW() WHERE id = 1;
-- → last_login_at 인덱스가 없다면 세컨더리 인덱스는 하나도 안 건드림. 싸다.

UPDATE users SET email = 'new@x.com' WHERE id = 1;
-- → idx_email 에서 기존 엔트리 삭제 + 새 엔트리 삽입. (이동이므로 2배 비용)
```

- **PK를 UPDATE하면 최악.** 클러스터 인덱스에서 행이 물리적으로 이동하고, 모든 세컨더리 인덱스가 PK 값을 들고 있으므로 전부 갱신된다. PK는 불변으로 둔다.
- PostgreSQL은 UPDATE가 곧 새 튜플 삽입이라, 바뀐 컬럼에 인덱스가 없고 같은 페이지에 자리가 있을 때만 **HOT update**로 인덱스 갱신을 건너뛴다. 인덱스를 많이 걸수록 HOT 조건이 깨져 인덱스 전부를 갱신하게 된다. → PostgreSQL에서 인덱스 과다는 UPDATE에 더 치명적.

# 4. 그래서 얼마나 느려지나

정확한 수치는 워크로드마다 다르지만 경향은 일정하다.

| 인덱스 수 | INSERT 처리량(상대) | 비고 |
| --- | --- | --- |
| PK만 | 100% | 기준 |
| +2~3개 | 60~80% | 대부분의 OLTP 테이블이 여기 |
| +6~8개 | 30~50% | 체감되기 시작 |
| 모든 컬럼 | 10~25% | 배치 적재가 몇 배로 늘어남 |

> 실제 값은 반드시 본인 환경에서 측정할 것. 컬럼 타입(무작위 문자열 vs 정수), 버퍼풀 크기, 디스크 종류에 따라 편차가 크다.

**측정 방법 (MySQL)**

```sql
-- 같은 데이터를 인덱스 있는 테이블/없는 테이블에 넣어보고 비교
SET profiling = 1;
INSERT INTO users_many_idx SELECT * FROM source_data LIMIT 100000;
INSERT INTO users_pk_only  SELECT * FROM source_data LIMIT 100000;
SHOW PROFILES;
```

# 5. 안 쓰는 인덱스 찾아내기

인덱스가 느리게 만드는 건 **쓰는 인덱스**가 아니라 대부분 **안 쓰는 인덱스**다. 먼저 이것부터 지운다.

## MySQL 8.0

```sql
-- 한 번도 안 쓰인 인덱스 (서버 재시작 후 충분히 운영된 뒤에 볼 것)
SELECT * FROM sys.schema_unused_indexes;

-- 중복/포함 관계 인덱스
SELECT * FROM sys.schema_redundant_indexes;

-- 인덱스별 실제 사용 통계
SELECT object_schema, object_name, index_name, count_star, count_read, count_write
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE object_schema = 'mydb'
ORDER BY count_star;
```

## PostgreSQL

```sql
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

## 중복 인덱스 패턴

```sql
KEY idx_a       (name)          -- ← 불필요. 아래에 포함됨
KEY idx_a_b     (name, email)   -- (name) 조건도 이걸로 처리된다
```

복합 인덱스 `(a, b)` 가 있으면 `(a)` 단독 인덱스는 **거의 항상 불필요**하다 (왼쪽 접두사 규칙). 반대로 `(b)` 단독은 필요할 수 있다. → [[복합 인덱스 컬럼 순서 정하기]]

# 6. 실무 가이드라인

## 걸어야 할 곳

- `WHERE` / `JOIN ON` / `ORDER BY` / `GROUP BY` 에 실제로 등장하는 컬럼
- FK 컬럼 (InnoDB는 FK 생성 시 자동으로 인덱스를 만들지만, 논리적 FK만 쓰는 경우 직접 걸어야 함)
- 핫패스 쿼리는 **커버링 복합 인덱스** 하나로 — 단독 인덱스 3개보다 복합 1개가 쓰기도 싸고 읽기도 빠르다

## 걸지 말아야 할 곳

- 카디널리티가 낮은 컬럼 **단독** (`is_active`, `status`, `gender`) — 옵티마이저가 어차피 안 쓴다. 복합 인덱스의 구성 컬럼으로 흡수시킨다 → [[복합 인덱스 컬럼 순서 정하기]]
- "혹시 나중에 쓸까봐" 만든 인덱스
- 필요 없는 `UNIQUE` (2-3 참고)
- 로그·이벤트처럼 **쓰기 폭주 + 조회는 가끔** 인 테이블 — 최소 인덱스로 두고 조회는 별도 분석 저장소로

## 숫자 감각

> OLTP 테이블 기준 **인덱스 5개 안쪽**이면 대체로 무난. 그 이상이면 "각 인덱스를 어떤 쿼리가 쓰는지" 하나씩 댈 수 있어야 한다.

## 대량 적재 시

```sql
-- 수백만 건 적재 전: 세컨더리 인덱스를 떼고 넣은 뒤 다시 만든다
ALTER TABLE users DROP INDEX idx_email, DROP INDEX idx_name;
-- ... 대량 INSERT (LOAD DATA / 배치) ...
ALTER TABLE users ADD INDEX idx_email (email), ADD INDEX idx_name (name);
```

건건이 트리를 고치는 것보다, 다 넣고 한 번에 정렬해 트리를 만드는 쪽이 훨씬 빠르다. 단 적재 중 해당 인덱스를 쓰는 조회가 없어야 한다.

기타 배치 팁:

```sql
SET autocommit = 0;          -- 건건 커밋 → 배치 커밋
-- 여러 행을 한 문장으로
INSERT INTO users (a, b) VALUES (1,2), (3,4), (5,6), ...;
```

# 7. SQLAlchemy 관점

```python
class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(BigInteger, primary_key=True)

    # index=True 를 습관적으로 붙이지 말 것 — 하나하나가 쓰기 비용이다
    email: Mapped[str] = mapped_column(String(255), unique=True)   # 조회 조건으로 쓰임 → OK
    name: Mapped[str] = mapped_column(String(50))                  # 인덱스 없음
    memo: Mapped[str | None] = mapped_column(Text)                 # 인덱스 없음

    __table_args__ = (
        # 단독 3개 대신 핫패스 쿼리용 복합 1개
        Index("idx_status_created", "status", "created_at"),
    )
```

> `index=True` 는 컬럼마다 별도 인덱스를 만든다. "일단 다 붙이고 나중에 정리"는 실제로 정리되지 않는다.

# 8. 정리

- 인덱스는 **읽기 속도를 쓰기 속도·저장공간과 맞바꾸는 것**이다. 공짜인 인덱스는 없다.
- 모든 컬럼 인덱스 = 읽기도 같이 느려질 수 있다 (버퍼풀 오염, 옵티마이저 혼선).
- 시작은 **PK + 실제 쿼리가 요구하는 최소 인덱스**. 느린 쿼리가 나오면 `EXPLAIN` 보고 그때 추가한다.
- 주기적으로 `sys.schema_unused_indexes` / `pg_stat_user_indexes` 로 죽은 인덱스를 걷어낸다.
